# BoxPilot 0.2.0

Release hardening: login throttling instead of account locks, sessions that end on a password reset, revocable share
links, hardened containers and uploads, and a round of frontend accessibility and usability fixes.

## Highlights

- **Login throttling per client IP** replaces the per-username account lock. Nobody can lock another person out by
  guessing their username any more. `POST /api/auth/login` and `POST /api/v1/auth/magic-login` answer **429** with a
  `Retry-After` header once a client has used up its failed attempts.
- **A password reset ends the user's sessions.** An admin who sets a user's password also ends that user's browser
  sessions, invalidates their outstanding magic links and revokes their MCP access.
- **Revocable public share links.** A box's public link (and its printed QR label) can be regenerated.
- **Safer uploads.** At most 25 megapixels per image, a limit on concurrent image decodes, clean 400/503 answers, and
  deleting a box removes its image files.
- **Hardened containers.** The backend runs as a non-root user with a read-only root filesystem and no extra
  capabilities; containers have memory limits; the frontend sends a Content-Security-Policy, HSTS and
  `X-Frame-Options: DENY`.
- **Health endpoint and clearer startup errors.** `/actuator/health` (status only) drives the compose healthcheck; a
  production start with missing settings lists all missing environment variables in one message.
- **Smaller session principal.** The password hash and the user entity are no longer stored in the session.
- **Frontend.** Theme colours meet WCAG AA contrast, routes are lazy-loaded, the public page has proper loading and
  error states, and adding several items in a row is faster ("save and add next").
- **Quality gates.** A GitHub workflow (`.github/workflows/ci.yml`) runs the backend and frontend suites on every
  push and pull request and a nightly browser E2E run; the E2E suite lives in `e2e/` with a compose overlay
  (`docker-compose.e2e.yml`).

## Upgrade steps (BREAKING)

Do these in this order.

1. **Back up first.** Flyway migrations only go forward, so the dump is your way back. Dump the database **and** copy
   `./images` at the same time, see [`docs/ops/backup-restore.md`](../ops/backup-restore.md).
2. **Check `ADMIN_PASSWORD`.** In production it must be at least **12 characters** (it must also still not be empty or
   `admin`). With a shorter value the backend refuses to start. Passwords set for users in the Admin Panel are now
   12 to 128 characters; existing passwords keep working.
3. **Fix directory ownership for the non-root backend.** The backend now runs as uid 10001. With the default bind
   mounts, once before `up`:
   ```bash
   mkdir -p logs images && sudo chown -R 10001:10001 logs images
   ```
   Without it the backend fails at startup because the image directory is not writable (the error message names
   the fix; log files cannot be written either). To stay root for the moment, uncomment `user: "0:0"` on the `backend` service in
   `docker-compose.yml` (add `cap_add: [DAC_OVERRIDE]` if the directories belong to another uid).
4. **Check `TRUSTED_PROXY_PATTERN`.** Login throttling counts by the client address Tomcat resolves from
   `X-Forwarded-For`, and it trusts that header only from the addresses matched by this Java regular expression (not
   CIDR). The default covers private address ranges and loopback, which fits Traefik on the compose network. If your
   proxy is outside those ranges, or the pattern is wrong, every visitor looks like the proxy and **shares one
   throttle counter**: a few failed logins then block everybody.
5. **Review environment variables** (all optional, defaults shown in `.env.example`):
   - `SESSION_COOKIE_SAME_SITE` (default `none`, unchanged behaviour). Use `lax` when frontend and API share a site.
   - `APP_LOGIN_THROTTLE_IP_LIMIT` (10), `APP_LOGIN_THROTTLE_IP_USER_LIMIT` (5), `APP_LOGIN_THROTTLE_WINDOW` (`15m`).
   - `APP_IMAGE_MAX_CONCURRENT_UPLOADS` (2).
   - `CSP_MODE` (`report`) and `HSTS_ENABLED` (`true` in `docker-compose.yml`). The frontend container derives
     `API_ORIGIN` from `VITE_API_BASE_URL`; do not set it yourself.
   - If `APP_MCP_ENABLED=true`: the origins of `VITE_API_BASE_URL` and `BACKEND_URL` must be identical, otherwise the
     backend now refuses to start. They always had to match for the Claude connect flow; only the check is new.
   - `POSTGRES_PORT` was removed from `.env.example`; nothing ever read it.
6. **Build and start.** The version is 0.2.0 in `backend/pom.xml` and `frontend/package.json`.
   ```bash
   docker compose build
   docker compose up -d
   docker compose ps          # backend must become healthy; the frontend starts after it
   ```
   Flyway applies V15 and V16 on the first start.
7. **Everyone signs in again once.** The session no longer contains the user entity, so existing sessions cannot be
   read. Nobody sees an error; the next request is simply anonymous and leads to the login page.
8. **Content-Security-Policy starts in report-only mode** (`CSP_MODE=report`). It blocks nothing; violations show up in
   the browser console. Open the main flows (login, box list, item with image, public page, label printing) with the
   console open. When it is quiet, set `CSP_MODE=enforce` in `.env` and run `docker compose up -d frontend`.

## Migrations

Flyway runs both automatically; neither can be undone by Flyway.

- **V15** (`clear_account_locks`) runs `UPDATE users SET locked_until = NULL, failed_login_attempts = 0` for every user
  that had a lock or a failure count. This is intended: locks no longer exist. The two columns stay in the table but
  are no longer written. Nothing else is deleted.
- **V16** (`add_users_sessions_valid_after`) adds a nullable `sessions_valid_after` timestamp to `users`. It is set to
  the current UTC time when an admin sets a user's password; a session older than that value is ended.

## Changes in behaviour

- **Throttle limits (defaults):** an IP may fail 10 logins in 15 minutes; one IP and username pair may fail 5. Magic-link
  redemptions that fail count against the IP only. `Retry-After` is the full window (900 s). Only failures count;
  a successful login neither counts nor resets anything.
- **A blocked IP stays blocked for correct logins too** until the window ends. Everybody behind the same address
  (office or home NAT) is affected together.
- **The account lock is gone:** the `/unlock` endpoint and the lock controls in the Admin Panel are removed. Disabling
  a user is still available.
- **Resetting your own password logs you out**, because the new marker also ends your current session.
- **Rotating a share link** (`POST /api/v1/boxes/{id}/rotate-share`) gives the box a new public UUID and new image
  tokens. Old links and printed QR labels stop working; reprint the labels.
- **Uploads:** images over 25 megapixels or files that are not images are rejected with 400; when all decode slots are
  busy the answer is 503 with `Retry-After: 5`.
- **Prod startup:** missing required environment variables are listed together, e.g.
  `Missing required configuration for profile 'prod': POSTGRES_USER, CLIENT_ID`.

## Removed endpoints

- `GET /api/v1/items` (list all items). Use `GET /api/v1/items/box/{boxUuid}` or `GET /api/v1/items/search`.
- `GET /api/v1/box-numbers/status`.
- The user `unlock` endpoint of the Admin API.

## Known limitations

- **The login throttle lives in the backend process.** Counters are not shared between replicas and reset on every
  restart; run one backend replica.
- **Shared addresses share a quota.** See the NAT note above; raise `APP_LOGIN_THROTTLE_IP_LIMIT` if that is a problem.
- **Every authenticated request reads the user from the database** to revalidate the session (role, enabled,
  password reset). This is not new; it is now part of the password-reset mechanism.
- **CSP is report-only by default** until you switch `CSP_MODE=enforce`.

## Rollback

Prerequisite: the database dump and image copy from step 1.

1. `docker compose stop frontend backend`.
2. Check out the previous release (commit `5e20b66`, the last commit before this release) and rebuild, or start the
   previous images if you kept them (`docker compose images` shows their IDs before you upgrade).
3. Delete the sessions in Redis; sessions written by 0.2.0 have a different shape than the previous build expects:
   ```bash
   docker exec boxcopilot-redis sh -c "redis-cli --scan --pattern 'spring:session:*' | xargs -r redis-cli del"
   ```
4. Start the old images: `docker compose up -d`. If the old container cannot write `./logs` and `./images`, you do not
   need to change them: the old image runs as root.

Data compatibility with the previous version, without restoring the dump:

- **V16** only adds a nullable column. The old backend does not map it and ignores it.
- **V15** only cleared lock data, nothing the old version depends on.
- Rotated share links, removed image files, passwords and magic-link state stay as they are and are readable by the
  old version. Flyway's history keeps V15/V16; the old build does not validate against it in production
  (`validate-on-migrate: false`).

Restore the dump and the image copy (see the backup guide) only if you want to discard everything written since the
upgrade.
